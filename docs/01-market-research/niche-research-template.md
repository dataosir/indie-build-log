---

## 基本信息
- **调研日期**：YYYY-MM-DD
- **Niche 简述**：用一句话说清楚这是帮【谁】解决什么【具体痛点】。
- **调研负责人**：CMO (一人扮演)

## 1. 痛点深挖 (Pain Point Analysis)

### 1.1 痛点描述
- **核心痛点**：用户在没有这个产品前，是如何痛苦地应付的？
- **痛点级别**：[ ] 止痛药 (Must-have，不解决会死/亏钱)  [ ] 维他命 (Nice-to-have，锦上添花)
- **痛点场景举例**：(引用 Reddit、GitHub Issue、或访谈中的原话)
  > *“我在 Reddit 的 r/java 看到有人抱怨：...”*

### 1.2 目标用户画像 (ICP - Ideal Customer Profile)
- **具体是谁**：(例：使用 Spring Boot 部署在 AWS 上的自由职业者)
- **预算决策权**：[ ] 极高 (有信用卡，能直接买)  [ ] 极低 (需经过复杂公司审批)

---

| :--- | :--- | :--- | :--- |
| **竞品 A** | (如：$49/mo) | | (如：部署复杂，配置需要写 100 行 YAML) |
| **竞品 B** | (如：$19/mo) | | (如：没有云端托管版，需要本地起服务) |
| **竞品 C (开源/替代方案)** | 开源免费 | | (如：缺乏图形化界面，报错信息晦涩) |

## 3. 核心切入点与差异化 (Our Wedge)

- **为什么用户会买我们的而不是竞品**：(例如：做极其傻瓜化的 1-Click UI 托管版本，价格只要竞品的 1/2，且针对 Java Native Image 做专门优化)
- **我们的最小功能边界 (One Killer Feature)**：MVP 阶段只实现这一个点。

## 4. 商业漏斗早期验证设计 (Validation Strategy)

- **流量入口 (Traffic Entrance)**：我们去哪里发帖或拦截早期流量？(例：去竞品 A 在 GitHub 上的 Issue 留言，去 r/aws 搜索痛点回帖)
- **验证载体 (Validation Asset)**：
  - [ ] 带有价格的 Landing Page
  - [ ] 带具体痛点筛选的 Waitlist 收集表 (Tally/Notion)
